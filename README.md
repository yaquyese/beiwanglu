## 项目一：飞鱼浏览器

更新日期：2026-11-04（Asia/Shanghai）
项目位置：Q:\独立Chromium浏览器

### 项目背景

用户在 Q 盘制作了一套独立 Chromium 浏览器，项目目录为 Q:\独立Chromium浏览器，名称为“飞鱼浏览器”。目录包含 Chromium 内核、独立的 User Data、下载目录、启动器、默认浏览器脚本、图标和“飞鱼网页翻译”扩展。用户说明这些项目内容是此前助手协助制作的。

浏览器启动器“飞鱼浏览器.exe”会从同目录运行 Chromium\chrome.exe，使用本地 User Data，并通过 --load-extension 加载“飞鱼网页翻译”。启动器源码位于“飞鱼浏览器-启动器.cs”。

### 用户需求与对话结论

用户很喜欢“飞鱼网页翻译”，希望在飞鱼浏览器里通过网页鼠标右键直接使用翻译。此前扩展只提供工具栏弹窗入口，用户希望增加：

1. 在网页空白处右键，可选择“用飞鱼翻译此网页（简体中文）”。
2. 选中网页文字后右键，可选择“用飞鱼翻译选中文字（简体中文）”。

翻译继续使用 Chromium 本机 Translator 模型；页面文字由本机处理，不发送给谷歌、微软或其他翻译服务。首次使用模型可能需要联网下载。

### 已做的修改

在 Q:\独立Chromium浏览器\飞鱼网页翻译 中：

- 更新 manifest.json 到版本 1.1.0，增加 contextMenus 权限和扩展后台 service worker。
- 新增 background.js，注册两个右键菜单，并在菜单点击时向当前页面注入翻译脚本。
- 新增 context-translate.js，实现网页全文翻译或所选文字翻译，并在页面右上角显示结果/进度。
- 保留原有 popup.html 和 popup.js 工具栏翻译入口。
- 确认 manifest.json 可解析，新增/更新的扩展文件为无 UTF-8 BOM 的 UTF-8 文本。
- 在 Q:\独立Chromium浏览器\使用说明.txt 中增加右键菜单用法说明。

### 设计与运行方式

- 右键菜单固定翻译成简体中文；工具栏弹窗仍可选择目标语言。
- 扩展版本号提升到 1.1.0，让 Chromium 识别扩展更新并触发菜单注册。
- 修改后需要完全退出并重新打开飞鱼浏览器，再使用右键菜单。
- 右键翻译入口运行在网页右上角的小面板中；首次使用时可能显示本机语言模型下载进度。

### 尚未完成的验证

此前没有实际打开飞鱼浏览器逐项点击验证右键菜单和模型翻译。后续建议确认：

1. 浏览器完全重启后，空白处右键是否出现“用飞鱼翻译此网页（简体中文）”。
2. 选中一段文字后右键是否出现“用飞鱼翻译选中文字（简体中文）”。
3. 两种入口是否都能显示右上角面板并返回翻译。
4. 如果菜单未出现，检查 Chromium 是否从该目录加载扩展、扩展后台 service worker 是否报错，以及是否有其他 Chromium 进程占用同一个 User Data。
5. 如果翻译失败，确认当前 Chromium 构建是否开放 Translator API、源语言判断是否适合目标页面，以及模型服务是否可连接。

## 项目二：悬浮复制器

更新日期：2026-11-04（Asia/Shanghai）
项目位置：Q:\悬浮复制器项目
项目状态：本轮主要功能、托盘行为、图标与 EXE 启动问题均已处理；用户确认当前可正常打开，后续可继续改进。

### 项目目标与最初需求

这是用户在云电脑上使用的 Windows 桌面小工具，用来减少登录 ChatGPT、GitHub、Google、加速器等服务时反复输入账号和密码的麻烦。用户希望打开后出现一个靠边、可拖动的小悬浮窗，保存若干常用文本或数字，点击即可复制到剪贴板。除账号、密码、网址外，还必须能新增任意字符或文本。

用户希望界面清爽、好看、接近 Tailwind 风格；窗口默认置顶但占用高度不要太大。用户对最小化有两个不同要求，后续不可混淆：窗口左上角的“−”按钮是最小化到 Windows 任务栏；点右上角“×”后弹出的“隐藏到托盘”才是隐藏到系统托盘。用户明确要求保留“−”按钮原有功能，不要把它改成托盘按钮。

### 已确认的产品决策

- 界面条目显示明文，用户明确要求关闭所有加密，也不要用星号遮挡。程序目录内的数据以明文 JSON 保存。
- 条目和设置都放在程序目录的 data 子目录，不主动写入 C 盘。此设计符合用户要求；使用前要保护好目录访问权限，因为条目可能含有账号或密码。
- 关闭“×”后可选择取消、隐藏到托盘或直接退出；可勾选“以后不再询问”，之后可在设置中调整关闭行为。
- 设置中可启用或停用托盘图标、设置窗口置顶，也可新增字符/文本。
- 左上角“−”始终最小化到任务栏；隐藏到托盘只通过关闭询问选择。
- 风格采用浅色卡片、圆角、蓝紫色强调和紫色星芒标识。

### 已完成实现与文件

- 悬浮复制器.ps1：Windows PowerShell 5.1 + WPF 实现界面、条目编辑、保存、复制、托盘与关闭逻辑。
- 悬浮复制器.exe：无控制台窗口的 64 位 EXE，供日常直接启动。
- 悬浮复制器.ico：程序图标文件；主窗口、任务栏和托盘使用同一个紫色星芒图标。
- 启动悬浮复制器.vbs：静默入口，优先运行同目录 EXE；若 EXE 不存在，则回退到同目录 PowerShell 脚本。
- data\vault.json：条目数据，明文保存。
- data\settings.json：关闭行为、托盘启用状态、窗口置顶等设置。
- README.md：项目目录中的使用说明和本地交接记录。

EXE 运行时仍需要同目录图标文件，数据目录也与 EXE 放在一起。PS1 不是 EXE 运行所必需的，但可作为源码和 EXE 缺失时的备用启动方式。VBS 也不是必需的，用户可直接双击 EXE；VBS 是另一种静默启动入口，两种方式共用同一个程序和 data 数据。

### 对话过程与问题处理记录

1. **新增条目与保存**：用户报告添加复制内容时保存失败。后续检查保存流程，要求保存失败时保留原数据；保存路径位于程序目录的 data 文件夹。
2. **剪贴板复制**：用户确认条目可以写入，但点击复制不能写进剪贴板。随后为复制按钮绑定当前条目内容，并为剪贴板写入增加回退处理。后续在运行时做过点击和剪贴板读回验证。
3. **条目右侧“⋯”菜单和删除**：菜单最初无法点击；后来编辑可以使用但删除没有反应。修复后删除能够执行，但用户继续发现删除后出现“已删除但窗口刷新失败”的误报。最后把数据保存和列表刷新分开处理，并移除了造成误报的状态栏 Text 写入；确认列表能刷新、删除错误提示与刷新提示不再混为一谈。删除保存失败时会恢复条目，避免界面和磁盘数据不一致。
4. **最小化与托盘曾被混淆**：用户多次澄清，左上角“−”最小化到任务栏没有问题，出问题的是点“×”后选择“隐藏到托盘”时图标消失。后续明确保留任务栏最小化按钮，只修关闭窗口的托盘隐藏路径。
5. **托盘图标生命周期**：隐藏窗口后托盘图标曾消失。关键处理是让 WPF Application 以显式关闭模式持续运行，并用 Application.Run 主消息循环托管窗口；隐藏主窗口时不结束应用进程，退出时才清理托盘图标并关闭应用。托盘菜单包含打开和退出，双击图标恢复窗口。实际验证过隐藏后托盘图标保留、恢复后窗口重新显示。
6. **关闭流程和设置保存**：用户报告点“直接退出”后还得再点一次叉；也报告“以后不再询问”时出现保存失败。关闭行为改为 Ask/Hide/Exit 的明确状态，保存偏好时补齐 CloseBehavior 属性；实际意图是关闭询问中选一次后可记住选择，之后能在设置里改回。
7. **托盘与再次启动**：窗口隐藏到托盘时，双击启动 VBS 最初不会显示窗口。后来用命名互斥体避免多开，并用本地激活事件让已有实例收到再次启动通知、恢复窗口，而不是再启动一个重复实例。验证 VBS 再次启动后只有一个应用实例。
8. **拖动区域**：用户指出鼠标移到标题文字上方一点就无法拖动，操作不自然。扩大了标题区域为透明背景的拖动 Grid，让标题栏中间空白也可拖动。
9. **默认尺寸**：用户觉得悬浮窗初始高度太长。默认高度缩短至 460 像素，并保留必要的最小尺寸与条目滚动区域。
10. **图标与 EXE**：用户要求把右下角系统托盘和任务栏上的 PowerShell 风格图标换成主界面左侧的紫色星芒。已生成 ICO 并设置窗口与 NotifyIcon 使用该图标；PS2EXE 打包时也将 ICO 设为 EXE 图标。产物为无控制台窗口 EXE。
11. **首次 EXE 启动报错**：首次打包后弹出“无法将参数绑定到参数 Path，因为该参数为空字符串”。原因是打包后的进程没有可用的 $PSScriptRoot，程序目录计算为空。已调整为源码启动取脚本目录、编译后优先取 AppDomain.CurrentDomain.BaseDirectory（EXE 所在目录），从而正确定位图标和 data。重新打包并启动后主窗口正常显示，数据仍在 Q:\悬浮复制器项目\data。
12. **直接退出后出现数字 0**：用户截图显示点“×”后选“直接退出”，退出前会出现标题为“悬浮复制器”、正文只有“0”的提示框，点确定后程序结束。原因是 WPF 的 Application.Run() 返回整数退出码 0；在无控制台 EXE 中它被当作脚本输出显示。已改为丢弃该返回值，并重新打包；实际打开关闭询问、点击“直接退出”验证，应用正常结束且不再显示“0”。

### 数据迁移、启动和交接注意事项

- 换新电脑时，最简单稳妥的办法是把整个“悬浮复制器项目”目录复制过去，尤其要带上 EXE、ICO 和 data 文件夹。VBS 与 PS1 可以保留作备用，也可只用 EXE 启动。
- 程序缺少 data 文件夹时会尝试自动创建，但新建的是空目录，不会恢复旧电脑条目。要迁移已有数据必须一起复制 data\vault.json 和 data\settings.json。
- 旧电脑的条目以明文保存在 data\vault.json；本轮没有把个人条目或真实密码上传到 GitHub README。公开仓库只保存项目交接文字，不要提交 data 文件。
- 若用户在设置里停用托盘，之后关闭行为选项会受托盘状态限制；若托盘不显示，先确认设置是否启用托盘，再检查程序是否仍在运行。区分通知区域隐藏图标和程序已退出。
- 重新构建 EXE 后，要从该 EXE 所在项目目录启动，并确保 ICO 与 data 同目录。VBS 会优先运行 EXE，想验证 PowerShell 源码时可在有控制台的情况下直接启动 PS1，以观察启动错误。

### 当前验证状态与后续

本轮确认：EXE 可以从项目目录启动并显示完整窗口；程序读取同目录的 vault.json/settings.json；托盘隐藏和恢复逻辑此前已实际验证；VBS 重复启动能唤醒现有实例；标题栏空白可拖动；复制和删除问题曾按上述路径修复；直接退出不再弹出 0。用户随后表示当前可以正常使用，本项目阶段性结束，未来可能继续改进。

目前没有已知必须立即处理的待办。以后继续时，先检查 Q:\悬浮复制器项目 的实际文件、EXE 时间戳与 data 文件，再根据用户报告处理；不要假设公开 README 中有用户数据，也不要覆盖“飞鱼浏览器”章节。用户偏好中文沟通、尽量自主完成并验证、交代修复根因；如需要调托盘，务必保留左上角任务栏最小化功能。

用户从零学习 Flutter、Dart、Material 3，并制作一个 Windows 图片处理工具。导入图片后可按证件照规格裁剪、压缩 JPEG 画质、替换蓝/白背景并保存到默认或自选目录。当前只做 Windows，Android 暂缓。使用 Flutter Widget 与自定义 Design System；不使用 HTML/CSS/Tailwind 作为 Flutter 界面样式。后续可独立扩展 AI 清晰化、图片合并。

- 单张图片导入（JPG/PNG/WebP/BMP/TIFF），一寸 295×413 px、两寸 413×579 px、方形 600×600 px 规格；预览实时显示裁剪框，滑杆调整裁剪位置。

### 当前限制

尚未实现精确目标文件大小压缩（目前只有 JPEG 质量调节）、批量图片和自由拖动裁剪框；未用真人照片评价抠图边缘，也未覆盖所有格式与 EXIF 旋转组合。具体证件照像素、300 DPI 推算、JPEG 输出和默认目录属于当前实现采用的临时默认值，尚未由用户逐项确认。

## 拾光工坊补充记录：保存后间歇性闪退（2026-11-04）

### 复现和影响范围

* 用桌面上的 JPEG 人像测试。默认一寸规格下，直接保存、以及蓝底抠图后保存，都曾发生闪退；两次都先生成了 JPEG 文件（295×413 px，约 24–26 KB），之后应用进程才消失。
* 进一步测试中，“两寸照 + 调整裁剪位置 + 保存”成功；“白底 + 调整裁剪位置 + 保存”成功，连续重复保存两次也成功。两寸输出 JPEG 约 43 KB。故障表现间歇性，尚未发现某个尺寸、裁剪或换底功能可稳定单独触发。

### 最可能的故障位置

保存流程位于 `lib/features/editor/editor_screen.dart` 的 `_export()`：图像处理由 `ImageExportService.createPhoto()` 完成，之后创建目标目录并调用 `File.writeAsBytes(..., flush: true)`。故障案例中，目标 JPEG 已落盘，说明图像编码和写文件步骤已成功；随后应用在保存成功后的界面更新阶段消失。Windows Application Error 事件（ID 1000）记录故障模块 `flutter_windows.dll`、异常 `0xc0000005`（访问冲突）、偏移 `0x3c1ea`；Flutter 调试输出同时反复报告 `Failed to update ui::AXTree` / 节点不在树中。没有 Dart 层可捕获异常。

综合这些证据，最可能出问题的是 Flutter Windows 引擎的 **AccessibilityBridge（Windows 无障碍桥接）** 在 UI 语义树更新失败后的原生访问冲突，而不是保存函数写坏图片或目录权限错误。Flutter 上游有相似的 [Windows AccessibilityBridge 崩溃记录 #175041](https://github.com/flutter/flutter/issues/175041) 和 [AXTree 更新失败记录 #182444](https://github.com/flutter/flutter/issues/182444)。

### 证据边界与后续

* 桌面自动化复现会连接 Windows UI Automation；它可能触发或放大引擎问题。尚未用完全不启用 UIA/读屏客户端的真人鼠标会话确认是否同样闪退。
* 未取得并符号化崩溃转储，因此无法确定具体是哪一个控件/语义节点先让无障碍树失效。AXTree 错误在成功保存的测试里也出现过，不代表每次都会马上崩溃。
* 本次没有改项目代码，也没有确认应用内的临时绕过方案。后续应在普通用户操作条件下复测；如仍闪退，保存 WER 转储并按崩溃栈定位。优先等待 Flutter 稳定版引擎修复，不要未经验证就关闭整个应用的无障碍能力。
* 详细事件记录、输出位置和恢复步骤见[拾光工坊详细交接](拾光工坊项目记忆与会话交接.md)。
